# Chess AI Agent (Backend) — Technical Notes

## Architecture & Overview

- **What it does / produces**: A FastAPI backend that generates personalized chess endgame lessons on demand. Given a free-text topic (e.g. "King and Pawn vs King", "Rook Endgames"), it runs a multi-step LLM agent pipeline and returns a **ZIP archive of PDF lesson files** (multiple lessons per request, each with a title, plain-English situation, FEN position, goal, strategy, move sequence, and an explanation linking the position back to generated strategic principles).

- **Agent workflow (LangGraph state machine)**: Implemented in `src/workflow.py` as a `StateGraph` (LangGraph) with a linear 4-node pipeline over a shared Pydantic state object (`EndgameState` in `src/models.py`):
  1. **`read`** — Uses an LLM (`gpt-4o-mini` via `langchain-openai`) to read a table of contents extracted from a source chess book and locate the start/end page range relevant to the user's topic, plus generate a web search query. Retrieves matching pages from a locally bundled PDF (`resources/100_Endgames.pdf`, "100 Endgames You Must Know" by Jesús de la Villa) using **PyMuPDF (fitz)** — extracting both text and page images (rendered to base64 PNG data URLs at 2x zoom) for multimodal LLM input.
  2. **`rules`** — Uses **Firecrawl** (`firecrawl-py`) to search the web and scrape matching pages (markdown format, truncated per-page), then prompts the LLM to synthesize 5–10 concise, imperative-style endgame principles from the scraped content.
  3. **`lesson`** — Prompts the LLM with the topic, generated principles, extracted book text, and the book page images (multimodal message) to produce 3–5 structured lessons via LangChain's `with_structured_output`, validated against a Pydantic schema (`ChessLesson`: parallel lists for `title`, `situation`, `FEN`, `goal`, `strategy`, `moves`, `rules_link`).
  4. **`pdf`** — Formats each lesson into text and renders it to a PDF file (via `fpdf`) written to a local `lessons/` directory; file paths are collected on the state object.
  - Each node has explicit exception handling that falls back to placeholder/error content rather than crashing the graph, so a failure in web scraping or book lookup degrades gracefully instead of aborting the whole run.
  - A 5th node (`calender`/Google Calendar scheduling of lessons via `google-api-python-client` OAuth) exists in `src/calender.py` and is wired into the graph but **commented out** in `_build_workflow` — present as built but currently disabled/dead in the active pipeline.

- **External services integrated**:
  - **OpenAI** (`gpt-4o-mini`) via `langchain-openai`/`langchain` — used for page-location reasoning, principle extraction, and structured multimodal lesson generation.
  - **Firecrawl** — web search + page scraping for supplementary endgame strategy content.
  - **Google Calendar API** (OAuth2, `google-auth-oauthlib`) — built but disabled; intended to auto-schedule generated lessons into a calendar.
  - A local, bundled proprietary/licensed PDF book (not an external API) acts as the primary knowledge source, parsed with **PyMuPDF**.

- **Data flow (request → output)**: Frontend (or `POST /lessons` client) sends `{ "query": "<topic>" }` → FastAPI clears any stale PDFs in `lessons/` → instantiates `Workflow()` and runs the LangGraph pipeline synchronously → collects generated PDFs → zips them in-memory (`zipfile`/`io.BytesIO`) → streams the ZIP back as `StreamingResponse` with `Content-Disposition: attachment` → server-side PDF files are deleted after zipping (stateless per-request; no persistent lesson storage).

- **Tech stack** (versions pinned in `uv.lock` / `pyproject.toml`):
  - **Language/runtime**: Python ≥3.10 (`.python-version` pins 3.10; Docker image uses `python:3.11-slim`)

  - **Google integration**: `google-api-python-client`, `google-auth-httplib2`, `google-auth-oauthlib` (Calendar scheduling, currently disabled)
  - **Config**: `python-dotenv` for `.env`-based secrets (`OPENAI_API_KEY`, `FIRECRAWL_API_KEY`)

## Agent Workflow

- Designed and implemented a 4-stage AI agent pipeline as a directed acyclic graph using LangGraph's `StateGraph` (`src/workflow.py`), with a single entry point (`read`) and strictly linear edges (`read → rules → lesson → pdf → END`) — no conditional branching or loops; each node is a pure function of a shared typed state object that returns a partial-state dict merged back into the graph state.

- Modeled the graph's shared state as a Pydantic `BaseModel` (`EndgameState` in `src/models.py`) carrying the pipeline's data as it accumulates across nodes: `topic` (user input), `piece_query` (LLM-derived web search query), `piece_rules` (LLM-synthesized principles), `book_text_content`/`book_pages` (extracted book text and page images), `lessons` (structured lesson dict), and `file_paths` (generated PDF paths) — giving each node typed, validated read/write access to only the fields it needs rather than passing raw dicts between steps.

- Built a 5th graph node (`_calender_events_step`) that integrates with the Google Calendar API (OAuth2 via `google-auth-oauthlib`) to auto-schedule generated lessons into time slots, but left it disabled (commented out of the compiled graph) — demonstrating the workflow was designed for extensibility beyond its currently active path.

- **Node 1 — book page location (`_read_book_step`)**: Uses `gpt-4o-mini` (via `langchain-openai`'s `ChatOpenAI`) in an analysis/reasoning role — prompts the model with the full book table of contents plus the user's free-text topic and asks it to return a strict 3-line output (0-indexed start page, end page, and a natural-language web search query), which is then parsed with `.splitlines()`. Wraps the entire step in a try/except that falls back to a generic query and an "error" placeholder on failure, so a malformed LLM response can't crash the pipeline.

- **Reference book location & extraction (`src/book.py`)**: The book's table of contents is pre-extracted once (via a separate offline script, `src/pdf_tutorials.py`, which walks the PDF's internal link annotations with PyMuPDF's `get_links()`/`LINK_GOTO` to build a page-number-indexed `TOC.txt`) and loaded at runtime as plain text for the LLM to reason over. Given the LLM-identified page range, `BookUtilities.get_book_extract` opens the bundled book PDF (`fitz.open`) and, per page, both (a) extracts raw text via `page.get_text()` and (b) renders the page to a 2x-scaled pixmap (`get_pixmap(matrix=fitz.Matrix(2, 2))`), encoding it as a base64 PNG data URL — producing a parallel text stream and an image-block list so the downstream LLM call can ground lesson generation in the book's actual diagrams, not just OCR'd/extracted text.

- **Web research via Firecrawl (`src/firecrawl.py`, orchestrated in `_web_scraper`)**: Uses the LLM-generated search query from Node 1 to call Firecrawl's `search()` API (capped to 4 results, markdown format), then iterates the result set and calls `scrape_url()` per result to pull each page's markdown content, truncating each scraped page to 1550 characters before concatenating — a deliberate token-budget control to keep the downstream LLM prompt bounded regardless of how much a scraped page returns. Wrapped in exception handling that degrades to an explicit "use your own knowledge" fallback string rather than failing the run if Firecrawl or a target site is unavailable.

- **Node 2 — principle synthesis (`_generate_rules_step`)**: Feeds the concatenated scraped web content into `gpt-4o-mini` in a synthesis role, using a system prompt (`Prompts.RULE_GENERATOR_SYSTEM`) that constrains output to 5–10 numbered, imperative-style rules grounded only in the supplied content (few-shot example rules included in the prompt to lock output format) — converting unstructured multi-source scraped text into a compact, consistent principles list consumed by the next stage.

- **Node 3 — structured lesson generation (`_lesson_generation_step`)**: The core generation step — combines the topic, synthesized principles, extracted book text, and the book page images into one multimodal `HumanMessage` (text block + image blocks) and calls `gpt-4o-mini` in generation mode via LangChain's `.with_structured_output(ChessLesson)`, forcing the model to return a validated Pydantic object rather than free text. `ChessLesson` defines each lesson field (`title`, `situation`, `FEN`, `goal`, `strategy`, `moves`, `rules_link`) as a parallel list, so one structured-output call produces multiple complete lessons (typically 3–5) in a single round trip, with index `i` across all lists representing lesson `i`. The system/user prompts (`src/prompts.py`) are heavily engineered: they specify an exact 7-field schema, embed a fully worked few-shot example (including a real FEN string and annotated move line), and impose explicit constraints (paragraph-length minimums per field, notation only allowed in the FEN and final move line, every cited principle must be explained rather than just referenced) to keep multi-lesson structured output consistent in depth and format. The structured response is converted from a Pydantic object into a plain dict (`{key: value for key, value in response}`) for storage in state.

- **Node 4 — lesson assembly & PDF rendering (`_pdf_generation_step`)**: Iterates the parallel lesson-field lists by index, reassembling each lesson into one formatted plain-text block per lesson (title, principles, situation, FEN, goal, strategy, moves, and the rules-link explanation, in a fixed section order), then hands each block to `save_text_as_pdf` (`src/pdf.py`), which uses `fpdf` to write a single-page-flow PDF (`multi_cell` for word-wrapped body text) to the local `lessons/` directory, returning the file's path back onto `state.file_paths` — this per-lesson text-to-PDF assembly is what the HTTP layer (`app.py`) later globs, zips, and streams back to the frontend as the request's deliverable.

## Most Complex Logic

**1. Multimodal grounding of lesson generation in actual book page images (not just extracted text)**
- *Resume bullet*: Engineered a multimodal LLM grounding pipeline that rasterizes located book pages to images via PyMuPDF (`get_pixmap` at 2x zoom), base64-encodes them as inline PNG data URLs, and merges them with extracted page text into a single LangChain multimodal `HumanMessage` (`{"type": "text", ...}` + `{"type": "image_url", ...}` content blocks) so structured lesson generation is grounded in the book's actual diagrams rather than text extraction alone.
- *Plain explanation*: Instead of just pasting extracted book text into the prompt, the agent also sends the model a picture of each relevant book page, so it can "see" diagrams and positions the raw text wouldn't capture.
- *Why it was hard / non-obvious*: Correctly constructing LangChain's multimodal content-block format (a list of typed dicts rather than a plain string) is an easy point of failure, and the number of images scales with the LLM-chosen page range with no explicit cap — a wide page range silently produces a proportionally larger multimodal payload.
- *Edge cases / gaps*: There's no limit on how many page images get attached, no image compression/downscaling beyond the fixed 2x render, and no handling for a page range that the LLM returns out of bounds for the actual PDF (`endgame_book[i]` would raise an unhandled `IndexError` inside `get_book_extract`, which is outside the node's own try/except since that wraps the LLM call, not the extraction call — actually both are inside the same try in `_read_book_step`, so it is caught, but degrades to the generic error fallback rather than retrying with a corrected range).

**2. Free-text "LLM-as-router" page-range resolution with minimal validation**
- *Resume bullet*: Implemented an LLM-driven routing step that has `gpt-4o-mini` read an entire book's table of contents and a free-text user topic, then return an unstructured 3-line response (start page, end page, search query) that the code parses positionally (`splitlines()` + integer casts) to drive downstream PDF page extraction — avoiding a hand-written keyword/TOC-matching algorithm in favor of LLM semantic matching.
- *Plain explanation*: Rather than writing string-matching logic to find "which pages talk about Rook Endgames," the agent just asks the LLM to read the table of contents and tell it which pages to look at.
- *Why it was hard / non-obvious*: This is a deliberately loose contract — the LLM's raw text output is trusted as a mini-protocol (exactly 3 lines, first two integer-parseable) with no schema enforcement, unlike the lesson-generation step which uses proper structured output. That inconsistency is itself worth noting: one step trusts prompt-engineered plain text, the other uses `with_structured_output`.
- *Edge cases / gaps*: `int(start_page)`/`int(end_page)` will raise `ValueError` if the model adds any extra commentary or the line count is off, and there's no check that the returned page range is within the actual document's bounds or that `start_page <= end_page`. Both failure modes are caught only by the node's blanket `except Exception`, which discards the specific cause and substitutes a generic hard-coded fallback query/content — functional but not diagnosable, and there's no retry-with-correction loop.

**3. Structured multi-lesson extraction via parallel-array schema, decoded from a single LLM call**
- *Resume bullet*: Designed a Pydantic output schema (`ChessLesson`) that encodes a variable number of complete lessons as index-aligned parallel lists (`title[i]`, `FEN[i]`, `moves[i]`, etc.) rather than a nested `List[LessonItem]`, forced via LangChain's `.with_structured_output`, then converted the returned Pydantic object to a plain dict via `{key: value for key, value in response}` (leveraging Pydantic `BaseModel`'s iterable protocol) so the PDF-assembly step can index into it directly.
- *Plain explanation*: One AI call generates several complete lessons at once, and the results come back as several same-length lists (all the titles, then all the FENs, etc.) that get zipped back together by position when building each PDF.
- *Why it was hard / non-obvious*: This is an unconventional structured-output shape — most developers would model this as a list of nested lesson objects. The parallel-array approach works but pushes an implicit invariant (all seven lists must be the same length and correctly index-aligned) onto the LLM's output with no explicit verification in code.
- *Edge cases / gaps*: `_pdf_generation_step` iterates `range(len(endgame_lessons['title']))` and indexes every other field at `i` with no length check — if the model ever returns mismatched list lengths (a real risk with structured output on long multi-field schemas), this raises an unhandled `IndexError` outside any try/except in that node, crashing the request. There's no schema-level `validator` enforcing equal list lengths, and no retry if the structured-output call itself fails validation.

**4. Multi-source web content aggregation with manual token-budget control**
- *Resume bullet*: Built a two-phase web research step (`_web_scraper`) that uses Firecrawl's search API to find up to 4 candidate pages for an LLM-generated query, then scrapes each individually and truncates each page's markdown to a fixed 1550-character slice before concatenation — a manual, code-level token-budget control (rather than relying on the LLM's context window or Firecrawl's own limits) to keep variable, unpredictable multi-source scraped content bounded before it's fed into the rule-synthesis prompt.
- *Plain explanation*: The agent searches the web, opens a handful of the top results, and grabs only the first chunk of each page's text so the combined content doesn't blow up the next AI call.
- *Why it was hard / non-obvious*: Scraped content length is inherently unpredictable across arbitrary websites; capping per-source rather than per-total-request is a reasonable but crude heuristic that trades completeness (a source's key content might be truncated away) for predictability.
- *Edge cases / gaps*: Both `search_for_rules` and `scrape_websites` catch exceptions internally and return `[]` on failure (search) or `[]` on scrape failure per-URL, and the outer `_web_scraper` has its own try/except with a "use your own knowledge" fallback string — so a fully offline/failed Firecrawl account degrades to letting the LLM rely on pretrained knowledge rather than failing the request, at the cost of silently lower-quality output with no signal surfaced to the caller that scraping actually failed.

## APIs, Data & Delivery

- **`GET /health`**: No parameters. Returns a Pydantic-modeled JSON body `{"status": "ok", "message": "Chess Endgame AI Agent is running"}` (`HealthResponse`). A basic liveness probe only — it doesn't check that `OPENAI_API_KEY`/`FIRECRAWL_API_KEY` are present or that the underlying LLM/Firecrawl services are reachable, so a "healthy" response doesn't guarantee `/lessons` will actually work.

- **`POST /lessons`**: Accepts JSON body `{"query": string}` (`LessonRequest`, validated by FastAPI/Pydantic — a missing/wrong-typed field is auto-rejected as a 422 before the handler runs). Runs the full LangGraph workflow synchronously inside the request/response cycle (no background job/task queue, no async offloading — the HTTP request blocks for the entire duration of the LLM calls, book extraction, and web scraping). On success, returns a **binary `StreamingResponse`** with `media_type="application/zip"` and a `Content-Disposition: attachment; filename="chess_lessons_<sanitized_query>.zip"` header — i.e. the frontend receives a downloadable file, not JSON; there is no endpoint that returns lesson data (FEN, title, strategy text, etc.) as structured JSON, so any in-browser rendering of lesson content on the frontend would require unzipping and parsing PDFs client-side rather than consuming an API response directly.

- **Artefact production & packaging**: Each of the 3–5 generated lessons is rendered to its own single-page-flow PDF (`fpdf`, `lesson{n}.pdf`) written to a local `lessons/` directory on the server's filesystem, then the handler globs all `*.pdf` files in that directory, writes each into an in-memory `zipfile.ZipFile` backed by an `io.BytesIO` buffer (`ZIP_DEFLATED`), rewinds the buffer, and streams it back — no PDF or ZIP ever touches persistent/cloud storage; everything is assembled in a scratch directory and RAM per request.

- **Filename sanitization**: The ZIP's filename is derived from the raw user query via a manual allowlist filter (`c.isalnum() or c in " -_"`), spaces replaced with underscores, and truncated to 50 characters — a reasonable, if minimal, defense against path traversal/header-injection via the `Content-Disposition` filename, implemented by hand rather than via a library.

- **Data storage, caching, persistence — effectively none**: There is no database, no cache layer, and no persisted lesson history — every `/lessons` call re-runs the entire pipeline from scratch (re-locates book pages, re-scrapes the web, re-generates lessons with the LLM), even for an identical or previously-served query. The `lessons/` folder is explicitly treated as scratch space: existing PDFs are deleted at the *start* of a request (`glob` + `os.remove` on all `*.pdf`) and again after zipping at the *end* — this doubles as informal cleanup but also means **`lessons/` is a single shared, unscoped directory with no per-request isolation (no request ID / subfolder / temp-dir)**, so two concurrent `/lessons` requests would read/write/delete each other's PDFs — a real race condition under any concurrent load, not just a theoretical one, since Uvicorn/FastAPI can serve requests concurrently by default.

- **Configuration & secrets handling**: Uses `python-dotenv`'s `load_dotenv()`, called redundantly in four separate entrypoints (`app.py`, `main.py`, `src/workflow.py`, `src/firecrawl.py`) rather than once centrally — harmless but a sign the app grew organically without a single composition root. `FIRECRAWL_API_KEY` is explicitly read via `os.getenv` and the service **fails fast with a clear `ValueError`** if it's missing (`src/firecrawl.py`); `OPENAI_API_KEY` has no equivalent explicit check in this codebase — it's implicitly required by `langchain-openai`'s `ChatOpenAI`, so a missing key would surface as a less friendly error from inside the LangChain/OpenAI client rather than an app-level message. Secrets are `.env`-file based only — `.env`, `credentials.json`, and `token.json` (Google OAuth artifacts) are correctly gitignored, but there's no `.env.example` documenting which variables are required, no secrets-manager integration, and no runtime validation step that checks both required keys are present before accepting traffic.

- **Error handling & validation**: Request-body validation is handled by FastAPI/Pydantic automatically (malformed JSON or wrong types → 422). The handler itself validates that `query` isn't empty/whitespace-only (400). All workflow/generation failures are caught by a single broad `except Exception` in the endpoint, logged via `traceback.print_exc()` (stdout, not a structured logger), and surfaced to the client as a generic 500 with the exception's string message included in the response body — which is convenient for debugging but leaks internal exception detail to callers, a rough edge for anything beyond a personal project. There is **no logging framework anywhere in the codebase** — all diagnostics are `print()` statements (many with emoji progress markers), which is fine for local/CLI use but means there's no log level control, structured logging, or log aggregation story for a deployed service. There is also no retry logic anywhere in the request path (LLM calls, Firecrawl calls, and book extraction each get exactly one attempt with a try/except fallback, not a retry-with-backoff).

- **How it runs / deploys**: Two independent entrypoints exist — `main.py` (CLI, `uv run python main.py [--topic ...]`, driving `Workflow` directly with no HTTP layer) and `app.py` (FastAPI service via `uvicorn app:app`, with `reload=True` hardcoded in its own `if __name__ == "__main__"` block — fine for local dev, not something you'd want in a production launch command). A `Dockerfile` is present (`python:3.11-slim`, installs `uv`, runs `uv sync --frozen --no-dev` for reproducible dependency install, exposes port 8000, `CMD uv run uvicorn app:app --host 0.0.0.0 --port 8000` without `--reload`) — so a containerized deploy path exists and correctly drops dev dependencies and hot-reload for the image. **What's honestly missing for production readiness**: no CI/CD pipeline (no `.github/workflows` or equivalent in the repo), no `HEALTHCHECK` instruction in the Dockerfile despite `/health` existing, no authentication/authorization on any endpoint, CORS wide open to `allow_origins=["*"]`, no rate limiting, no request size/timeout limits around the long-running synchronous LLM/scraping call, and no automated tests. The Google Calendar scheduling feature is fully coded (OAuth flow, token refresh, event creation) but disconnected from the live graph — present but non-functional in the current build.
